# 초급 보급 의뢰 예제 통합 안내

이 문서는 새 Landscape의 NPC 배치 완료 보고가 아니다. 격리 패킷을 통합·컴파일한 에디터 소유자가 의뢰 Data Asset 하나를 작성하고, 실제 후보 맵에 연결해 검증하는 절차다. 이전 `FiveVillageGraybox20261110` 설치/전체5의뢰 렌더 시험은 과거 회귀 전용으로 보존한다.

## 소스와 데이터 연결

1. 원본이 퀘스트 미설치이면 `Integration/village-quests-intro-source.patch`를 적용한다. `94cd66e` editable 패킷이 이미 통합됐으면 `village-quests-intro-delta.patch`만 적용한다. 이전 패킷과 중복 적용하지 않는다. 세 공용 TutorialNPC/Widget hook도 필요하다. 원본의 인벤토리·전리품·피격 취소·컨트롤러 변경은 그대로 유지한다.
2. 공유 소유자가 UHT/Editor를 빌드하고 에디터를 다시 로드한다. `Rogue10mVillageQuestDataAsset`, 새 메서드/속성, VillageQuest 자동화18개가 같은 체크포인트에서 보이는지 확인한다. 이 Work에서는 빌드/에디터를 실행하지 않았다.
3. 프로젝트 소유 경로에 새 `Rogue10mVillageQuestDataAsset`을 만들고 `Reset To Intro Supply Example`을 호출한다. 이 버튼은 기존 데이터 전체를 예제로 교체하며 맵/앵커를 비운다. 새 에셋이나 검토용 복제본에 사용한다. Undo 동작을 검증했다고 가정하지 않는다.
4. `SupportedWorld`는 현재 실제 후보 맵을 직접 선택한다. `LayoutOriginCm`/`LayoutRotation`과 NPC·목표의 로컬 좌표/높이를 실제 지형에 맞춘다. 예제의 ±500cm 목표는 작은 편집 예시이며 제작 JSON의 미터 좌표가 아니다. 넓은 원본 맵·전체 배치를 복원하지 않는다.
5. `Quests`의 활성 행만 완성한다. 내부5슬롯은 유지하고 필요 없는 행의 `Enabled`를 끈다. 활성 행마다 목표2개가 필요하고 동일 VillageId에는 현재 활성 의뢰1개만 지원한다. 비활성 행의 미완성 대사/전투 데이터는 로드·생성하지 않는다. 활성 선택 이야기에는 원본/분석/보고 역할이 모두 필요하므로 예제는 이를 전부 끈다.
6. NPC 외형과 애니메이션은 기존 `NpcPresentation`으로 연결하고, 목표 mesh·label·반경과 대사·보상을 편집한다. 기본 Quinn/Cube는 기존 코드의 예제 fallback이며 새 아트 소유/배치 검증의 증거가 아니다. 목표는 가방 아이템/RNG 대신 런의 사실로 기록하여 일반 가방 부족으로 영구 소실되지 않는다.
7. `Validate Configuration`을 실행해 `LastValidationPassed`와 이유를 확인한다. 맵 바인딩이 없는 예제는 의도적으로 실패한다. 선택한 월드가 존재하고 충돌·동선이 맞는지는 별도 검증한다. 저장 후 에디터 재시작/cold reload에서도 값이 유지되는지 확인한다.
8. 후보 맵에 Director 하나를 명시적으로 배치하고 `QuestDefinition`에 이 에셋을 연결한다. 기존 GameMode/GameState와 정상 런 진입 경로를 유지한다. 이 단계에서 예제의 기대 생성 수는 NPC1·탐색 표식2·전투 몬스터0이다.

`Scripts/Editor/CreateIntroVillageQuestDefinition20261113.py`는 새 Data Asset만 작성하는 선택 도구다. 기본 호출은 계획만 반환한다. 에디터 소유권 인계/새 클래스 빌드 확인/새 목적지/대상 월드를 명시해야 실행하며, 맵 열기·저장·Director 배치를 하지 않는다. 실제 UE에서 이 도구를 실행한 것은 아니다.

## 실제 플레이 인수

- 정상 필드 진입 후 자동 대화 없이 F로 NPC를 열고, 선택/닫기/거리 이탈·입력 복구를 확인한다.
- 수락 전 두 목표 회수→수락 시 Ready, 또는 수락→역순 회수→Ready를 각각 확인한다. 같은 표식은 한 번만 기록되고 사라졌다 재생성돼도 중복 보상이 없다.
- 보고 보상은 설정값1회다. 같은 런 재방문·NPC/Director 재생성 후 완료 반응과 영수증을 보존한다. 아이템 보상으로 변경한 후보는 가방 부족→Ready 유지→정리 후 재수령을 확인한다.
- 실제 런 종료→정상 귀환/재진입에서 새로운 의뢰·관측·보상 영수증이 초기화되는지 확인한다. 아래 테스트의 Running 이벤트 주입은 이 전체 여행 검증을 대신하지 않는다.
- 중앙 보스 직행로·다른 마을·초소·학습 조건은 의뢰 완료와 무관하게 유지한다. 중상급 비급은 이 보상 메뉴에 넣지 않는다. 현재 예제는 골드만 지급한다.
- 통합 체크포인트를 Cook/Windows package하고 실제 Game EXE에서도 동일 경로와 저장/재시작을 확인한다.

## 검증을 구분해서 읽기

기존 VillageQuest 자동화11개에 이번 Selection3개와 Lifecycle4개를 더해 총18개를 작성했다. 모두 UE 빌드·실행 대기다. 신규 Lifecycle는 실제 component/collector/inventory delegate를 사용하지만 overlap과 Running 이벤트를 주입하므로 물리 이동·NPC UI·여행·저장을 증명하지 않는다. 오프라인 Python mock 검사는 작성 도구의 분기만 증명한다. 이전 native575/656·launcher185 결과는 이번 실행 통과로 합산하지 않는다.

기존 전투 의뢰에는 조건부 회복 공백이 남아 있다. 비플레이어/미귀속 피해로 목표 몬스터가 죽으면 소비 영수증이 먼저 남아 목표 진행 없이 재생성이 차단될 수 있다. 정상 관측 공격은 플레이어 귀속이지만, 환경 처치 복구는 검증되지 않았다. 초급 예제에는 전투 목표가 없으며 이 공백을 숨기거나 임의 면역/처치 귀속 정책을 추가하지 않는다.

이 예제는 큰 거점1·초소1·사냥터1·독립 비급 발견까지의 전체 제작 수직 경로를 완료하지 않는다. 최신3큰거점+5초소·일반15/중간4/최종1 정책의 시작용 독립 패킷이다.

기존 일반 `RewardItem` 형식은 아이템의 비급 등급/획득 정책을 자동 판별하지 않는다. 보상을 수정하는 소유자가 최신 획득처와 실제 아이템 매핑을 대조한다. 이번 예제/작성 도구의 골드 전용 검사는 전체 보상 시스템의 비급 정책 검증을 대신하지 않는다.
